# D2k 扩展：32/48/64 MetaDrive CPU worker 采样吞吐量

日期：2026-11-17。正式 GitHub Actions [#44029425146](https://github.com/Kryponitee/drive-like-a-living-system/actions/runs/44029425146)：**SUCCESS**。

## 目的与控制

上一轮 [D2k #44028935956](https://github.com/Kryponitee/drive-like-a-living-system/actions/runs/44028935956) 在每组 8,192 个总环境步下，4/8/16/32 workers 吞吐量分别为 298.9/327.7/542.9/962.9 env steps/s。用户希望继续测试 48 与 64 workers。

为了形成**同批次的严格可比较数据**，本轮不是只单独测试 48 和 64，而是**重新测试 32/48/64**，且将每组的总环境步预算统一为 **24,576**（可被 32、48、64 整除）。此改变的目的在于避免新旧测试的场景长度和测试时长差异造成不公平的速度排名；上一轮数据保留但不参与同一决策指标。

**一致条件**：MetaDrive 0.4.3，地图3、交通密度0.10，259D结构化观测；同一个冻结的 SB3-Contrib RecurrentPPO 300,032-step 模型及保存的 VecNormalize 观测统计；独立 spawn 子进程；模型确定性推理；每 worker 2 次热身；无 PPO 权重更新、无优化器、无专家示范生成，原模型与 DLS 环境不变。每配置顺序独立执行，禁止跨配置争用资源。

报告与逐设置 JSON 位于数据盘 `/mnt/datasets/lxb/dls/reports/d2k-extended/`，主要汇总文件为 `worker-scaling-summary.json`。

## 实测

| workers | 总环境步 | 每 worker 测量步 | 测量秒数 | 吞吐量 env steps/s | 启动与 reset 秒数 | 所有 worker RSS 合计 MiB |
|---:|---:|---:|---:|---:|---:|---:|
| 32 | 24,576 | 768 | 44.6 | **551.3** | 6.9 | 19,836 |
| 48 | 24,576 | 512 | 32.4 | **759.1** | 5.5 | 29,430 |
| **64** | 24,576 | 384 | **26.6** | **925.4** | 6.0 | 39,098 |

启动前可用系统内存约201.3 GiB；64 workers 进程 RSS 合计约38.2 GiB，不过逐进程 RSS 会重复计算共享映射页，不能据此断言真实物理消耗恰好38.2 GiB。

同批次相对性能：

- 48 vs 32：`759.1/551.3≈1.38×`；
- 64 vs 32：`925.4/551.3≈1.68×`；
- 64 vs 48：`925.4/759.1≈1.22×`。

按事前预注册「达到最高吞吐量的90%以内优先选用较少 workers」规则，**64 workers 为当前最佳选择**，因为48 workers仍比64 workers慢约18%。所有三个设置均成功完成。

## 必须保留的限制

1. **不能将上一轮 32 worker 的 962.9 steps/s 和本轮的 551.3 steps/s 当作“性能损失”或 48/64 的共同基准。** 旧测试总测量8,192环境步，新测试24,576步；单 worker 推进时间不同，会触发不同的episode终止/重置与不同后续场景；此外两轮主机并发负载无法保证相同。差异成因尚未分离，不能武断归因于任何一个因素。
2. 这是冻结模型的 **MetaDrive采样 + CPU LSTM推理吞吐**，**不包括** PPO 反向传播、价值更新、优化器和收集-更新同步，因此不是完整训练的 steps/sec。
3. worker 数变化意味着每个 worker 的场景推进深度不同。环境步数已匹配，但轨迹/场景分布没有强制做到逐步一致；此测试仅用于系统性能选型，不用来推断模型成功率。
4. 64 workers 使用了全部128个逻辑线程中的相当一部分；在同时运行GPU训练、数据服务或其他同学任务时，吞吐可能变化。未测96/128 workers，不宣称64为全局最优。

## 实施决策

下一次**优化器包含在内**的短时训练吞吐量测试，以64 workers为候选，并保留32 workers作为稳健基准；先核对 PPO 的 `n_steps × n_envs` 批量与优化次数，避免因并发变动导致梯度更新规模变化而把工程速度当成算法结果。

在正式 A/B/C 训练中，尽可能复用经验证的官方并行采样、GAE、PPO数据结构和归一化；不更改独立科学模型架构和旧 BC checkpoint。当前测试**不涉及模块通信因果性**，也不改变 D2j 随机初始化 LSTM 在300k环境步只有2/24新场景到达的事实。
