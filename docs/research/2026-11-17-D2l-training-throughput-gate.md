# DLS D2l — 64-worker PPO 完整训练性能验收（预注册）

2026-11-17，D2k 已验证冻结模型采样时 64 workers 优于 32/48。但原测试不含网络反向传播和 optimizer，不代表真实 PPO 训练吞吐。因此只进行**一次**完整训练链路验收，不以此反复扩展工程研究。

## 需要回答的唯一问题

**64 个 MetaDrive CPU workers 在包含官方 RecurrentPPO 反向传播和优化器更新时，是否仍带来实际训练加速？**

## 复用与变量控制

- 全部复用 D2j 官方 `MlpLstmPolicy` 300,032-step 权重、`VecNormalize`、SB3-Contrib 2.6.0 + 现有 PyTorch/MetaDrive 环境；不安装包、无新专家、无 A/B/C 参数更新。
- 同一份模型/归一化分别在 32 与 64 workers 上**独立加载**，同批次顺序运行；仅改并行环境数，不改策略架构、动作分布、PPO 学习率、n_steps128、minibatch128、n_epochs4、GAE/clip 参数。
- **每配置额外采样并训练16,384个环境转移**。32 workers 是4次 rollouts ×4,096帧，64 workers 是2次 rollouts ×8,192帧；理论上两组的 epoch×minibatch 数据处理总量相同。**注意两配置的策略更新频率和 stale-policy 期限不同**，所以只比较墙钟吞吐，不能比较驾驶收益或等价的学习动态。
- 新训练场景区间：各 worker [14000 +80i, 14080+80i)，与 D2j/D2k、BC、保留评测种子不重合。
- 记录初始化时间、总训练耗时、collection 时间、非 collection 时间（包含 PPO backward、optimizer 和框架开销）、总训练FPS、CPU内存RSS，以及终止 episode 数。重采样过程不修改任何原始 checkpoint。
- 窗口相对短，结果视作**短时性能门槛**。若64 workers 比32的完整训练FPS低超过10%，重新考虑32；否则遵从用户已选的64，进入正式模型适配。无需继续测试96/128。
- 工程验收不能代替科学实验；正式 A/B/C 对照仍需相同轨迹分布、参数/FLOPs/环境预算匹配，并做多种子验证。

## 后续滚动

**D2m**：仅做已有 A/B/C 的循环状态与慢环时钟接入标准 PPO 数据结构的正确性测试，禁止换成普通 LSTM 代替模块结构，不重复上一个自写 PPO 的完整实现。

**D2n**：以 D1 BC 权重初始化，采用成熟 PPO 框架组件，等预算 A/B/C 闭环优化，在合理规模下同时评估能力是否保留与是否有改善。通过后进入 D3 模块间消息干预和反馈补偿主实验。

**收口条件**：D2l 完整训练运行通过 + D2m A/B/C 策略状态与概率重放通过，即停止新增泛用预检并进入 D2n。若某项失败，只修相应明确问题，不借口再开大范围工程探索。
